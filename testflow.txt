================================================================================
1. TESTING OBJECTIVES & QA STRATEGY
================================================================================
The objective of this testing flow is to validate that:
  - All 3 system tiers (React Frontend, FastAPI Backend, MongoDB Atlas) communicate
    flawlessly with zero unhandled exceptions.
  - The Computer Vision pipeline (SSD MobileNet + 68 Landmarks + 128-d embeddings)
    accurately recognizes enrolled faces and rejects low-confidence matches.
  - Interactive liveness challenge blocks photo/screen replay spoofing attempts.
  - Ray-casting GPS polygon geofencing allows check-in ONLY within the office box.
  - Role-Based Access Control (RBAC) securely isolates Admin, Manager, and Employee
    capabilities.
  - All approvals and manual overrides write an immutable audit trail in MongoDB.


================================================================================
2. PRE-TEST PREREQUISITES & ENVIRONMENT CHECKLIST
================================================================================
Before running tests, verify the following prerequisites:

1. Python Environment:
   - Python 3.10 or 3.11 installed.
   - Virtual environment exists at `.venv/`.
   - Dependencies installed via: `pip install -r requirements.txt`
   - Key packages: `fastapi`, `uvicorn`, `pymongo`, `opencv-python-headless`,
     `dlib` (or `face_recognition`), `requests`, `python-dotenv`.

2. Node.js & Frontend Environment:
   - Node.js (v18 or higher) and npm installed.
   - Frontend dependencies installed at `frontend/node_modules/`:
     ```cmd
     cd frontend
     npm install
     cd ..
     ```

3. MongoDB Atlas Connection:
   - Check `backend/.env` file contains a valid `MONGODB_URI`:
     `MONGODB_URI=mongodb+srv://...`
   - Note: If MongoDB is offline, the backend gracefully falls back to `mongomock`,
     allowing all logic tests to run without database interruption.

4. Hardware & Permissions:
   - Working webcam (or Virtual Camera mode enabled in UI).
   - Browser location/GPS permission granted for `http://localhost:3000`.


================================================================================
3. SYSTEM EXECUTION (LAUNCHING BACKEND & FRONTEND)
================================================================================

METHOD A: ONE-CLICK LAUNCHER (RECOMMENDED)
------------------------------------------
Simply double-click or run from command prompt:
```cmd
run_app.bat
```
What `run_app.bat` does automatically:
  1. Checks for `.venv\Scripts\python.exe`.
  2. Ensures `frontend\node_modules` exists (runs `npm install` if missing).
  3. Kills any conflicting processes listening on ports 8000 and 3000.
  4. Starts FastAPI on `http://127.0.0.1:8000` with auto-reload.
  5. Waits for MongoDB connection to initialize.
  6. Starts Vite React dev server on `http://localhost:3000`.
  7. Automatically opens your default web browser to `http://localhost:3000`.

METHOD B: MANUAL COMMAND-LINE LAUNCH
------------------------------------
Terminal 1 (Backend):
```cmd
.venv\Scripts\activate
uvicorn backend.main:app --reload --host 127.0.0.1 --port 8000
```
Terminal 2 (Frontend):
```cmd
cd frontend
npm run dev
```

TO STOP THE APPLICATION:
------------------------
Run:
```cmd
stop_app.bat
```
This cleanly terminates both processes on ports 8000 and 3000.

6. SECURITY & NEGATIVE EDGE-CASE TEST SUITE
================================================================================

--------------------------------------------------------------------------------
6.1 TEST S1: ANTI-SPOOFING & LIVENESS CHALLENGE FAILURE
--------------------------------------------------------------------------------
Objective: Ensure static photos or spoofing attempts are blocked.
Action (API Level):
  Send POST request to `/api/employee/attendance/mark` with:
  `{"employeeId":"EMP001", "isCheckOut":false, "livenessVerified":false, "withinRadius":true}`
Expected Response:
  - HTTP Status: `400 Bad Request`
  - Detail: "Liveness verification failed. Potential spoofing or replay attempt detected."
  - Database: No attendance document created.

--------------------------------------------------------------------------------
6.2 TEST S2: GPS GEOFENCE BOX BOUNDARY VIOLATION
--------------------------------------------------------------------------------
Objective: Ensure check-in from outside office polygon is strictly blocked.
Action (API Level):
  Send POST request to `/api/employee/attendance/mark` with coordinates outside office:
  `{"employeeId":"EMP001", "latitude": 13.0827, "longitude": 80.2707}` (Coordinates in another city)
Expected Response:
  - HTTP Status: `400 Bad Request`
  - Detail: Contains "Outside office geofence box: your GPS position ... is not inside the premises."
  - Result: Check-in rejected.

--------------------------------------------------------------------------------
6.3 TEST S3: ROGUE ADMIN REGISTRATION WITH INVALID PASSKEY
--------------------------------------------------------------------------------
Objective: Prevent unauthorized users from creating Admin accounts.
Action:
  Attempt POST `/api/auth/register/admin` with `securityPasskey: "WRONG_SECRET"`.
Expected Response:
  - HTTP Status: `403 Forbidden`
  - Detail: "Invalid Administrator Passkey. Contact Security or use default AMS-ROOT-2026."

--------------------------------------------------------------------------------
6.4 TEST S4: INVALID LOGIN CREDENTIALS & ERROR HANDLING
--------------------------------------------------------------------------------
Objective: Verify invalid emails/passwords do not leak sensitive information.
Action:
  Attempt POST `/api/auth/login` with `identifier: "fake@company.com"`, `password: "wrong"`.
Expected Response:
  - HTTP Status: `401 Unauthorized`
  - UI shows clear error alert: "Account not found. Please verify your Email or Employee ID."

--------------------------------------------------------------------------------
6.5 TEST S5: DUPLICATE / DOUBLE CHECK-IN DETECTION
--------------------------------------------------------------------------------
Objective: Prevent an employee from submitting multiple check-ins on the same day.
Action:
  Submit a second check-in request (`isCheckOut: false`) on the same calendar date.
Expected Response:
  - System detects existing check-in timestamp.
  - Automatically preserves original check-in and prompts employee to Check-Out instead.

--------------------------------------------------------------------------------
6.6 TEST S6: FORGOT PASSWORD OTP LIFECYCLE
--------------------------------------------------------------------------------
Objective: Test password recovery security.
Action:
  1. POST `/api/auth/forgot-password/request` with `identifier: "admin@company.com"`.
     - Returns 4-digit code (e.g., `8421`).
  2. POST `/api/auth/forgot-password/verify` with incorrect code `0000`.
     - Expected: `400 Bad Request` ("Invalid or expired OTP verification code").
  3. POST `/api/auth/forgot-password/verify` with correct code.
     - Expected: `200 OK`.
  4. POST `/api/auth/forgot-password/reset` with new password.
     - Expected: `200 OK`. Password updated in Atlas.

7. MONGODB ATLAS DATABASE INTEGRITY VERIFICATION
================================================================================
If you have access to MongoDB Compass or MongoDB Atlas web console:

1. Open database: `attendance-monitoring-system`.
2. Inspect `users` collection:
   - Verify documents have `password_hash` populated (never plain text password).
   - Verify unique indexes exist on `email` and `employeeId`.
3. Inspect `attendance` collection:
   - Check that documents have `confidence`, `withinRadius: true`, and `livenessVerified: true`.
4. Inspect `leave_requests` collection:
   - Verify that approved leaves have `reviewedBy`, `reviewedByName`, and `remarks`.
5. Inspect `approval_audits` collection:
   - Verify audit trail documents contain `actorName`, `targetEmployeeId`, and `reason`.
6. Inspect `settings` collection:
   - Check `global_settings` document contains `geofencePolygon` array with 4 vertex points.

8. TROUBLESHOOTING & COMMON ISSUES RESOLUTION GUIDE
================================================================================

Issue 1: "Ports 8000 or 3000 Already in Use"
  Solution: Run `stop_app.bat` to terminate lingering node or python tasks, or run
  `run_app.bat` which automatically terminates conflicting port processes.

Issue 2: "Webcam Access Denied / Black Camera Box"
  Solution:
  - Check browser camera permission (click the padlock icon in URL bar -> Allow Camera).
  - If using a laptop without an active webcam, toggle "Use Virtual Camera Simulation"
    in the UI to test biometric flows without hardware camera.

Issue 3: "Outside Office Geofence Box Error"
  Solution:
  - The system validates that your GPS is inside the campus polygon.
  - When testing remotely, toggle "Simulation Mode" or click "Use Demo Office Location"
    in the UI radar component. This mocks the office centroid coordinates.

Issue 4: "MongoDB Connection Timeout"
  Solution:
  - Check your internet connection (MongoDB Atlas requires internet).
  - Ensure your IP address is whitelisted in MongoDB Atlas Network Access.
  - The application automatically falls back to in-memory `mongomock` if Atlas is
    unreachable, allowing tests to run offline.
